# Explanation and Reference

Read only the section that matches the selected reader job.

## Explanation

Use an explanation when the reader needs a mental model.

- Name the question, mechanism, forces, and boundary.
- Connect abstractions to concrete examples.
- Explain why the system has its current shape, including meaningful
  alternatives, tradeoffs, and limits.
- Distinguish established behavior from interpretation or recommendation.
- Avoid turning the explanation into an untested procedure.

Complete the explanation when the reader can reason about a new relevant case,
not merely repeat the wording.

## Reference

Use reference documentation when the reader needs accurate facts about a
defined interface or system surface.

- Mirror the structure and canonical terminology of the subject.
- State inputs, outputs, defaults, constraints, errors, side effects, and
  compatibility within the declared scope.
- Prefer generation from schemas, code, metadata, or other authoritative
  artifacts when practical.
- Use examples only to clarify usage; link task guidance elsewhere.
- Check completeness and freshness against the described machinery.

Complete the reference when the declared surface is accurate, consistently
organized, and searchable without presenting interpretation as fact.
